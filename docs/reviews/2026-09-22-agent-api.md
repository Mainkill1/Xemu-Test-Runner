# API-first agent workflow review

Base: `f82004c37cf7f70390db65cc3937e45667ac92b8`.
Branch: `feature/api-first-agent-workflow`; PR #14.

## Problem

The existing file API could receive a file into FileRoot, but POST /api/v1/jobs explicitly refused submission and instructed the caller to stage a package directory in Pending. Agent use consequently required filesystem access despite the intended API-first architecture.

## Implementation boundary

Add a package-level workflow around the existing queue and upload engine. Keep drafts under Pending/.agent-jobs until an explicit validated submission atomically publishes the payload. Reuse FileUploadStore for streamed/resumable/hash-verified uploads and reuse the existing runner's JobDefinition/Preflight and result/control routes.

Do not add a shell executor, separate service, duplicate telemetry collector, archive extractor, auto-installer or run-evidence editor. Changes are confined to the networking workflow, its discovery/client and operational documentation. Job plans remain editable only before claim.

## Responsibilities

- AgentJobStore: API-owned package identity, draft plan/file operations, atomic withdrawal/cancellation/publication.
- AgentJobStore.Operations: asynchronous validation/submission/cloning, durable receipts and restart reconciliation.
- AgentJobStore.Downloads: declared-payload download handles.
- EmbeddedHttpServer.Agent: HTTP decoding, bounds, status/error envelopes and links.
- AgentApiCatalog: one route catalog for agent discovery and workflow OpenAPI.
- runner_api.py: optional remote-machine HTTP client; stdout JSON, no SSH fallback.

## Race and failure decisions

A queue claim and withdrawal are competing directory renames. Neither modifies a visible package in place. Repeated create/submit requests use stable client IDs and published queue location rather than inventing a second attempt.

A draft permits one mutation at a time, including uploads and background operations. Rejected request bodies close their connection rather than becoming the next HTTP request. File transfer uses the existing committed-offset and verify-before-publication store, not a new unverified copy path.

Windows state readers use FileShare.Delete so polling does not block atomically replaced metadata. A synchronous mutation returns post-operation actions instead of advertising its own transient reservation as a stuck busy job. Async failures retain validation results and progress rather than overwriting them with only an exception message.

Heavy operations are tracked for their full lifetime. Starting a benchmark during an existing upload/copy/hash operation can still cause interference; the activity record identifies it. This change does not claim a scheduler-level no-overlap guarantee.

## Remaining qualification and limits

No full API-only xemu/native-GPU workload was run in the authoring container. Existing CI and Python syntax checks are distinct from validating the new lifecycle on a live tester. Verify create/upload/edit/submit/collect and then exercise disconnects, revision conflicts, claim-vs-withdraw, invalid digest, interrupted cloning, Windows atomic metadata reads and restart-after-publication.

Operations are cancelled with the runner lifetime; they are not resumable computation across a process restart. Receipts reconcile the outcome and payload uploads retain committed offsets. No API can bootstrap a stopped runner. Runtime configuration/OS administration, arbitrary legacy-package repair, active policy-bypassing kill and results retention/deletion are deliberately outside this workflow.
